Az alábbiakban egy olyan egyszerű Express-alkalmazást javaslok, amellyel jól szemléltethető a diákoknak az authentication (hitelesítés) és az authorization (jogosultságkezelés) közötti különbség.

A példát a nálad használt technológiákhoz igazítom:
- Node.js + Express
- JavaScript ES modulok (type: module)
- JWT tokenes hitelesítés
- Middleware-alapú jogosultságellenőrzés
- Két jogosultsági szint: user és admin
- Egyelőre adatbázis nélkül, hogy a működés könnyen követhető legyen.
1. Először értsék meg a két fogalmat
Authentication
Hitelesítés – Ki vagy te?

A rendszer ellenőrzi, hogy a felhasználó valóban az-e, akinek mondja magát.

Példa: felhasználónév és jelszó ellenőrzése, majd JWT token kiadása.


Authorization
Jogosultságkezelés – Mit tehetsz?

A rendszer ellenőrzi, hogy a már hitelesített felhasználó elvégezheti-e a kért műveletet.

Példa: egy normál felhasználó megtekintheti a profilját, de nem törölhet felhasználókat.


A folyamat:
1. Bejelentkezés

Felhasználónév + jelszó

2. Authentication

Jelszó ellenőrzése, JWT token létrehozása

3. Kérés a szerverhez

Authorization: Bearer TOKEN

4. Authorization

Jogosultság ellenőrzése

5. Művelet végrehajtása

Engedélyezés vagy 403 Forbidden

4. Felhasználók létrehozása
A példa kedvéért két felhasználót hozunk létre. A jelszavakat bcrypt segítségével hash-eljük.

server.js:

import express from "express";
import bcrypt from "bcryptjs";
import dotenv from "dotenv";

import apiRoutes from "./routes/api.js";

dotenv.config();

const app = express();

app.use(express.json());

// Demo felhasználók
const users = [
    {
        id: 1,
        username: "tanulo",
        password: "123456",
        role: "user"
    },
    {
        id: 2,
        username: "admin",
        password: "admin123",
        role: "admin"
    }
];

// Jelszavak hash-elése induláskor
for (const user of users) {
    user.password = await bcrypt.hash(user.password, 10);
}

// A felhasználók elérhetővé tétele a route-ok számára
app.locals.users = users;

app.use("/api", apiRoutes);

app.listen(process.env.PORT || 3000, () => {
    console.log("Szerver elindult: http://localhost:3000");
});



Megjegyzés: a felhasználók most csak a memóriában vannak. A következő lépésben ezt adatbázissal lehet helyettesíteni.
5. Authentication middleware – authenticate.js
Ez a middleware végzi a hitelesítést.

Feladatai:
1. Megkeresi az Authorization fejlécet.
2. Ellenőrzi, hogy van-e Bearer token.
3. Ellenőrzi a JWT aláírását és lejáratát.
4. Siker esetén elhelyezi a felhasználó adatait a req.user objektumban.
5. Hiba esetén 401-es státuszkódot küld.
middleware/authenticate.js:

import jwt from "jsonwebtoken";

export default function authenticate(req, res, next) {

    const authHeader = req.headers.authorization;

    // Van-e Authorization fejléc?
    if (!authHeader) {
        return res.status(401).json({
            message: "Nincs bejelentkezve!"
        });
    }

    // Bearer token kinyerése
    const [type, token] = authHeader.split(" ");

    if (type !== "Bearer" || !token) {
        return res.status(401).json({
            message: "Hibás token formátum!"
        });
    }

    try {
        // JWT ellenőrzése
        const decoded = jwt.verify(
            token,
            process.env.JWT_SECRET
        );

        // Felhasználói adatok átadása
        req.user = {
            id: decoded.sub,
            role: decoded.role
        };

        next();

    } catch (error) {
        return res.status(401).json({
            message: "Érvénytelen vagy lejárt token!"
        });
    }
}



Tanári magyarázat: itt még nem vizsgáljuk, hogy a felhasználó admin-e. Csak azt ellenőrizzük, hogy hitelesített felhasználóról van-e szó.
6. Authorization middleware – authorize.js
Ez már a jogosultságokat vizsgálja.

A middleware paraméterként megkapja az engedélyezett szerepköröket.

middleware/authorize.js:

export default function authorize(...allowedRoles) {

    return (req, res, next) => {

        // Van-e hitelesített felhasználó?
        if (!req.user) {
            return res.status(401).json({
                message: "Először jelentkezz be!"
            });
        }

        // Jogosultság ellenőrzése
        if (!allowedRoles.includes(req.user.role)) {
            return res.status(403).json({
                message: "Nincs jogosultságod a művelethez!"
            });
        }

        next();
    };
}



Itt érdemes kiemelni a diákoknak:
- 401 Unauthorized: nincs megfelelő hitelesítés.
- 403 Forbidden: a felhasználó hitelesített, de nincs jogosultsága.
A két státuszkód közötti különbség fontos.
7. API végpontok – routes/api.js
Itt kapcsoljuk össze a hitelesítést és a jogosultságkezelést.

import express from "express";
import bcrypt from "bcryptjs";
import jwt from "jsonwebtoken";

import authenticate from "../middleware/authenticate.js";
import authorize from "../middleware/authorize.js";

const router = express.Router();

// AUTHENTICATION
// Bejelentkezés
router.post("/login", async (req, res) => {

    const { username, password } = req.body;

    if (
        typeof username !== "string" ||
        typeof password !== "string" ||
        !username.trim() ||
        !password
    ) {
        return res.status(400).json({
            message: "Hiányzó vagy hibás adatok!"
        });
    }

    // Felhasználó keresése
    const user = req.app.locals.users.find(
        u => u.username === username
    );

    if (!user) {
        return res.status(401).json({
            message: "Hibás felhasználónév vagy jelszó!"
        });
    }

    // Jelszó ellenőrzése
    const validPassword = await bcrypt.compare(
        password,
        user.password
    );

    if (!validPassword) {
        return res.status(401).json({
            message: "Hibás felhasználónév vagy jelszó!"
        });
    }

    // JWT létrehozása
    const token = jwt.sign(
        {
            role: user.role
        },
        process.env.JWT_SECRET,
        {
            subject: String(user.id),
            expiresIn: "1h"
        }
    );

    res.json({
        message: "Sikeres bejelentkezés!",
        token
    });
});


// AUTHENTICATION
// Minden bejelentkezett felhasználó elérheti
router.get("/profil",
    authenticate,
    (req, res) => {

        res.json({
            message: "Sikeres hozzáférés a profilhoz!",
            user: req.user
        });
    }
);


// AUTHENTICATION + AUTHORIZATION
// Csak admin érheti el
router.get("/admin",
    authenticate,
    authorize("admin"),
    (req, res) => {

        res.json({
            message: "Üdvözöllek az admin felületen!",
            user: req.user
        });
    }
);


// Több szerepkör is engedélyezett
router.get("/tananyag",
    authenticate,
    authorize("admin", "user"),
    (req, res) => {

        res.json({
            message: "A tananyag elérhető!",
            user: req.user
        });
    }
);

export default router;

10. Javasolt tanórai bemutatási sorrend
Szerintem érdemes a programot nem egyszerre bemutatni, hanem fokozatosan felépíteni.
1. Middleware nélkül: készítsenek egy /profil végpontot, amely bárki számára elérhető.
2. Authentication: tegyük kötelezővé a bejelentkezést. Próbálják ki token nélkül és hibás tokennel.
3. Authorization: korlátozzuk az /admin végpontot. Először próbálják ki user, majd admin szerepkörrel.
4. Middleware: mutassuk meg, miért előnyös a hitelesítést és a jogosultságkezelést külön fájlba szervezni.
Egy érdekes tanulói feladat
Bővítsék az alkalmazást az alábbi végpontokkal:
Végpont	Jogosultság
GET /api/konyvek	user, admin
POST /api/konyvek	admin
PUT /api/konyvek/:id	admin
DELETE /api/konyvek/:id	admin
GET /api/felhasznalok	admin
GET /api/profil	user, admin

Ezzel már egy kisebb könyvnyilvántartó REST API jogosultságkezelését is megvalósítják.
Néhány fontos biztonsági megjegyzés
Ez a példa oktatási célra készült. Éles alkalmazásban még szükséges:
- A felhasználók adatbázisban történő tárolása.
- A JWT titkos kulcsának megfelelő, véletlenszerű generálása és biztonságos kezelése.
- A jogosultságok szükség szerinti újbóli ellenőrzése az adatbázisból.
- A bemeneti adatok szerveroldali validálása.
- A token biztonságos tárolása. Böngészős alkalmazásban az HttpOnly, Secure és megfelelő SameSite beállítású cookie is megfontolandó.
- A JWT payload nem titkosított, ezért abba jelszót vagy bizalmas adatot nem szabad tenni.
Különösen fontos tanári megjegyzés: a 401 és 403 különbségét mindenképpen saját példán keresztül mutatnám be. Ez az egyik leggyakrabban félreértett része az API-k jogosultságkezelésének.
